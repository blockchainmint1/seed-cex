# Pockets

- Which pocket coins HME Wallet can't hold comes only from POCKET_SPECS.hmeToday via src/lib/pockets/hme-support.ts (tested); every swap-back-to-TSD warning uses it, revoking warns but is never blocked, and a TSD swap never buys a coin Seeds can't sell back. Why: after a revoke Seeds deletes its key, so those coins are recoverable only by recovery phrase.
- New chains follow the checklist in docs/hme-wallet-extra-pockets.md: POCKET_SPECS entry, exact key format in KEY_FORMATS, test vectors from an outside reference plus a cross-check against HME Wallet's own derivation code, then list it in request_optional. A coin with signing=planned is accepted in links but never offered for deposit. Why: HME Wallet skips optional coins it doesn't know, so the two sides never have to ship on the same day, and a deposit must never be a one-way trip.
- Pocket key families, address encoders, signers and read-only chain I/O live in src/lib/pockets/; any seed (wallet, vault, typed, operator) is reduced to account 1106–2105 pocket keys via derive.ts and wiped, and the optional coins (every POCKET_SPECS entry with hmeToday=false) link only in instant-access mode. Why: Seeds owns chain support so HME Wallet doesn't have to, without ever holding savings branches.
- Native XLM/TON/SUI builders are stellar-tx.ts, ton-tx.ts and sui-tx.ts; ed-send.server.ts reads/estimates before KMS unlock, records ids before one submission, and checks delivery. edSendStage in ed-send-rules.ts gates both deposits and withdrawals (review → audited tester sends → open); member protection checks stay in withdraw/. Why: key acceptance never silently activates an unaudited money path.
- Native sends persist immutable expiry evidence with the txid; missing transactions fail only after chain-proven expiry (TON seqno zero never expires automatically). TON balance/send calls share tonEndpoint and pre-sign wallet state is checked against TONAPI. Why: a timeout or imprecise payment value must never permit a duplicate withdrawal.
- TRC-20 USDT uses tron-usdt.ts / tron-usdt.server.ts and the existing TRX 1106/0/0 key: pinned contract, six decimals, local TriggerSmartContract transfer, two-server spend/permission checks, exact simulation, live full-burn fee budget before KMS, immutable tx evidence and unique per-kind txid records before broadcast, and two finalized exact Transfer receipts. THORChain uses the same transfer plus its checked outer memo (no router/allowance); tronUsdtStage gates deposits and every sending/purchasing path. Why: token support must not inherit native balances, count one send twice or expose an unaudited one-way deposit.
