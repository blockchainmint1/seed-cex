# Key sign-in (coin / outside wallet)

- "Start with a coin" / "Use another wallet" accounts are made only through the Seeds Key hand-off: /key-signin starts a single-use request (browser keeps a secret, server stores its hash), the separate Seeds Key page POSTs /api/public/key-signin/submit with a keySigninMessage signature (coin = Seeds' own text signed by TXC m/44'/696969'/0'/0/0; evm/sol = Sign-In with Ethereum/Solana layout bound to the SEEDS_KEY_URL host, nonce = challenge, signed via personal_sign / ed25519) plus a sealed hm-link-delegate access payload, and only the starting browser can claim the session. Rules (pocket numbering, re-sign-in keeps the link, placeholder emails, wallet-pocket message) live in rules.ts (tested); the Key page copies rules.ts + seeds-key-reference.ts + src/lib/pockets/ unchanged (docs/seeds-key-page.md, test vectors in handoff.test.ts). Why: Seeds must never receive a recovery phrase, and both sides must derive identical pockets.
- Coin/wallet accounts are found by profiles (identity_kind, identity_address), never by email; their auth email is a non-deliverable placeholder that every send path skips (isPlaceholderEmail in loadRecipient/deliver) and UI hides (shownEmail). A real email is added only via a confirmed code (account_email_codes) or by attaching an HME membership with both the live session token and a signed HME ticket (attach.server.ts). Why: anyone can make a phrase, so identity is the key itself, and accounts never merge on email alone.
- Never change walletPocketMessage (Sign-In with Ethereum/Solana layout, fixed nonce + issued-at, HKDF label "seeds-key wallet pocket v2") or the Seeds Key host once members use it, and never add a Seeds-held salt (Bobby, Nov 21). Why: outside-wallet pockets are rebuilt from that exact signature, wallets only warn on look-alike sites for the standard layout, and members must be able to rebuild their pocket without Seeds.
- Every key sign-in shows pairingCode(challenge) on both screens and the Seeds tab asks "is this yours?" (shortKeyName) before verifyOtp; adding an email needs a fresh 2FA code when 2FA is on and alerts Telegram; coin/wallet sign-up bursts page admins (shouldAlarmNewAccounts, alarm only); old requests are pruned hourly by the market-snapshot job. Why: auditor K2/K3/K5/K6 — QR hijack, silent factor swap, botnets.
- A key sign-in bringing different pocket keys than the active link (keysDiffer) is never applied by submit: it is held on key_signin_requests.pending_link, the member is warned on Telegram (with a revoke button) and by email first, and only the starting screen can apply it via confirmKeyReplace (fresh authenticator code checked server-side when 2FA is on, 5 tries, 10 min, compare-and-set on the old link) — replace.server.ts. Identical keys stay silent. Bobby chose this (auditor's version) over refusing outright, Nov 21. Why: a phished sign-in signature plus made-up keys must not silently take over future deposits.
- The new-account alarm fires at or above the hourly level, at most once per 10 minutes (single-row key_signin_alarm compare-and-set). Why: an exact-multiple check can be stepped over.
