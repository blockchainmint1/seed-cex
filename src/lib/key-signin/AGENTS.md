# Key sign-in (coin / outside wallet)

- "Start with a coin" / "Use another wallet" accounts are made only through the Seeds Key hand-off: /key-signin starts a single-use request (browser keeps a secret, server stores its hash), the separate Seeds Key page POSTs /api/public/key-signin/submit with a keySigninMessage signature (coin = Seeds' own text signed by TXC m/44'/696969'/0'/0/0; evm/sol = Sign-In with Ethereum/Solana layout bound to the SEEDS_KEY_URL host, nonce = challenge, signed via personal_sign / ed25519) plus a sealed hm-link-delegate access payload, and only the starting browser can claim the session. Rules (pocket numbering, re-sign-in keeps the link, placeholder emails, wallet-pocket message) live in rules.ts (tested); the Key page copies rules.ts + seeds-key-reference.ts + src/lib/pockets/ unchanged (docs/seeds-key-page.md, test vectors in handoff.test.ts). Why: Seeds must never receive a recovery phrase, and both sides must derive identical pockets.
- Coin/wallet accounts are found by profiles (identity_kind, identity_address), never by email; their auth email is a non-deliverable placeholder that every send path skips (isPlaceholderEmail in loadRecipient/deliver) and UI hides (shownEmail). A real email is added only via a confirmed code (account_email_codes) or by attaching an HME membership with both the live session token and a signed HME ticket (attach.server.ts). Why: anyone can make a phrase, so identity is the key itself, and accounts never merge on email alone.
- Never change walletPocketMessage (Sign-In with Ethereum/Solana layout, fixed nonce + issued-at, HKDF label "seeds-key wallet pocket v2") or the Seeds Key host once members use it, and never add a Seeds-held salt (Bobby, Nov 21). Why: outside-wallet pockets are rebuilt from that exact signature, wallets only warn on look-alike sites for the standard layout, and members must be able to rebuild their pocket without Seeds.
- Every key sign-in shows pairingCode(challenge) on both screens and the Seeds tab asks "is this yours?" (shortKeyName) before verifyOtp; adding an email needs a fresh 2FA code when 2FA is on and alerts Telegram; coin/wallet sign-up bursts page admins (shouldAlarmNewAccounts, alarm only); old requests are pruned hourly by the market-snapshot job. Why: auditor K2/K3/K5/K6 — QR hijack, silent factor swap, botnets.
- A key sign-in bringing different pocket keys than the active link (keysDiffer) is never applied by submit: it is held on key_signin_requests.pending_link, the member is warned on Telegram (with a revoke button) and by email first, and only the starting screen can apply it via confirmKeyReplace (fresh authenticator code checked server-side when 2FA is on, 5 tries, 10 min, compare-and-set on the old link) — replace.server.ts. Identical keys stay silent. Bobby chose this (auditor's version) over refusing outright, Nov 21. Why: a phished sign-in signature plus made-up keys must not silently take over future deposits.
- The new-account alarm fires at or above the hourly level, at most once per 10 minutes (single-row key_signin_alarm compare-and-set). Why: an exact-multiple check can be stepped over.
- Account pages branch on the member's sign-in kind via useMyIdentity (components/account/use-identity.ts) and the wording/step rules in src/lib/account/sign-in-kind.ts (tested): coin/wallet members never see HME Wallet link/re-link controls; their "re-link" is signing in again with the same key (SignInAgainButton → /key-signin, same pocket via keepExistingLink/pocketFor), and withdrawals show the email step first (withdrawContext needsEmail, NEEDS_EMAIL_TO_WITHDRAW). Why: their pocket comes from their own key, and one shared rule source keeps Security, Overview, Withdraw, the guide and server messages saying the same thing.
- HME Vault link (signed request v2): the manifest carries `vault_request` only on the live addresses (seeds.honest.money + key.seeds.honest.money) when a Vault signer is configured, built by vault-request.ts (tested) over the bytes from vault-protocol.ts — a verbatim copy of Seeds Key's file, re-copy, never edit. The Ed25519 key lives in AWS KMS via SEEDS_VAULT_KMS_KEY (id seeds-vault-kms-2026-11, always wins; set without the AWS login = no signer; the old seed secret is deleted and its id retired); each request is signed once, verified, and stored on key_signin_requests.vault_request; only its public half is published (/api/public/key-signin/vault-signer, docs/vault-request-signer.md) and Key/Vault pin it by hand, never fetched. created_at and expires_at come from one clock reading (keyRequestWindow). A new key = new id + overlap per the rotation steps. Why: Vault is offline and must refuse any request Seeds didn't make, so the recipient can't be swapped.
- Extra passwords (BIP39 passphrase) are an optional `passphrase` on coinIdentityKey/buildHandoff (NFKD via seedPassphrase, "" = unchanged); identity and pockets must use the same one, and it never leaves the device. Why: Vault seeds with a password are a different wallet, and Vault must not fork derivation code.
- "Use HME Vault" is /key-signin?kind=vault: same request as a coin sign-in (Vault signs as kind coin, so the account is a coin account), passed to Seeds Key as ?kind=vault so it opens its Vault scan directly (older Key builds fall back to the coin screen with its Vault toggle). The screen shows Vault only when vaultAvailable (same gates as vaultRequestFor) says the manifest will carry a signed request. Why: Vault requests only exist on the live addresses, so members must not be sent to a Key page that hides Vault.
- Link mode (Bobby, Nov 22): Honest.Money members link a coin / HME Vault / outside wallet as their trading pocket from the Security tiles (components/wallet/LinkOptions.tsx: big HME Wallet tile + accordion with pros/cons) via /key-signin?link=true → startKeyLink (signed-in, identity_kind hme only, request.link_user_id) → submit hands off to link.server.ts (keyLinkProblem/keyLinkOutcome in rules.ts, tested): never creates, merges or signs into another account; a key with its own account or active elsewhere is refused; a different key than the active link is refused (revoke first); a new key is always held, warned about on Telegram + email before it applies (warnKeyLinkHeld), and applied only by the member's own session via confirmKeyLink after "confirm it's you" (src/lib/step-up; shows shortKeyName); confirmHeldReplace refuses to cross link mode and sign-in replacement; the same key again is a refresh. The key stays a pocket, not a second sign-in. Pocket wording follows the link (hme_links.key_kind + pocketSource in sign-in-kind.ts), not the sign-in kind. HME Wallet submit refuses to replace a seeds_key link. Why: one account, one pocket, and a hijacked QR can't slip someone else's keys into a member's pocket.
- One phrase, one account: a coin / wallet sign-in never opens a new account for a key that was ever another account's pocket (secondAccountProblem). Why: two accounts must never share one pocket.
